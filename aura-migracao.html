causa Inputs que não foram declarados

No classic, a lista inputs: de uma tool define o que o orquestrador consegue preencher.

Um tópico passa argumento por binding mesmo sem o input estar declarado — foi o que salvou sua abertura. O modelo, não: o que não está declarado como entrada dinâmica, para ele não existe.

Cinco tools ficaram sem inputs obrigatórios. Três delas não são chamadas por nenhum tópico — então dependem só do orquestrador, e por isso estão mortas.

O dicionário de colunas DAX no input query, o formato JSON do userEnteredFields, e o SILENT TOOL. DO NOT generate text da tool de detalhes — que virou só "Obter os detalhes de um único item de trabalho".

A mecânica que faz virar conversa de mão dupla

A mensagem proativa só pode ir para o chat pessoal do gestor com o agente. Parece limitação, mas é justamente o que faz o seu cenário funcionar:

O canal de volta já existe por construção. Sem webhook, sem polling, sem ler a caixa de e-mail de ninguém.

Work IQ: as duas pegadinhas

Ele existe no standard — entra em Ferramentas → Model Context Protocol → Work IQ. Mas duas coisas decidem a questão.

💸 Custo

Para agentes customizados, Work IQ é cobrado por consumo em Copilot Credits e não entra na licença do Microsoft 365 Copilot.

Você saiu do motor do GitHub Copilot exatamente porque ele cobrava até para testar. Ligar Work IQ reintroduz cobrança por consumo pela porta dos fundos.

🔐 De quem é o dado

Work IQ roda no contexto do usuário logado. Ele lê a caixa, a agenda e as conversas de quem está falando com o agente.

Não lê a caixa do gestor. Para o ciclo de cobrança, ele não substitui a mensagem proativa do Teams — que, aliás, não custa crédito nenhum.

Onde valeria a pena depois: Work IQ Calendar para marcar a reunião de rebaseline assim que o gestor confirmar a data nova. Aí é enriquecer o seu contexto, que é a fronteira certa.

Bloco A — as quatro correções

  1. Update ProjectAdicionar type fixo e userEnteredFields com a descrição do formato JSON. Teste: mudar o Note de um work item de teste. Hoje não acontece nada.
  2. Power BI Portfolio DatabaseAdicionar query como entrada dinâmica, com o dicionário de colunas. Teste: "quais são os watermelons?" fora do tópico de abertura.
  3. Obter detalhes do work itemAdicionar id e restaurar o SILENT TOOL. Teste: "me traz o work item 376" — o ID está no seu próprio log.
  4. Query Devops BUAdicionar queryId com a tabela de GUIDs por BU.

Bloco C — sim, são dois tópicos separados

Um arquivo = um tópico. Não cole os dois no mesmo. Eles são as duas metades do mesmo ciclo:

→ cobranca-gestor

A ida. Você pede para cobrar. Ele lê o work item, monta o rascunho, espera sua aprovação e envia pelo Teams.

← resposta-do-gestor

A volta. O gestor responde com a data. Ele valida, mostra o de-para, espera confirmação e grava no DevOps.

Em cada um: Tópicos → + Adicionar um tópico → Do zero → menu ⋯ → Abrir editor de código → apagar tudo, colar o .yaml, salvar.

Por que fazer isso no standard vale a pena

Aqui o Question e o ConditionGroup executam. A aprovação antes de mandar mensagem para outra pessoa, e a confirmação antes de gravar no DevOps, são portões reais — não instruções que o modelo pode contornar.

Na experiência nova, com skills, isso viraria texto. Essa diferença é o argumento mais forte a favor da trilha que você escolheu.

Todo GUID, operationId, coluna DAX e reference name Custom.* foi extraído dos exports do próprio agente e conferido linha a linha. Nada foi inventado. Onde não deu para verificar sem acesso ao tenant — o binding dos campos do Teams e o formato de data do Custom.GoLiveDate — está marcado explicitamente, com o teste para descobrir e o que trocar.

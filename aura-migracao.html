Os cinco defeitos concretos

Não é uma impressão de que “está estranho”. São cinco coisas verificáveis no arquivo.

01 Azure DevOps desapareceu por inteiro

$ grep -c "visualstudioteamservices" Aura_Agent.yaml
0

Sumiram as três consultas por Query ID, o GetWorkItemDetails e o UpdateWorkItem. Suas instruções ainda mandam “use Azure DevOps com o ID exato” — o agente lê, tenta obedecer e não acha ferramenta nenhuma.

02 A Master DB Search perdeu os bindings

    dialog:
      kind: ConnectorTool
      operationId: ExecuteDatasetQuery
      # ← acabou aqui. NÃO existe bloco toolInputs.

Sem toolInputs, os três parâmetros caem em “preencher com IA”. O modelo não tem como adivinhar os GUIDs do workspace e do dataset — eles não estão em lugar nenhum do contexto dele. Resultado: HTTP 400 sempre.

O detalhe cruel: as variáveis com os valores certos existem no arquivo. Só não foram ligadas à tool. Essa é provavelmente a correção que sozinha destrava metade dos erros de hoje.

03 O motor analítico não foi recriado

A Power BI Portfolio Database tinha groupid e datasetid fixos, query livre para a IA, e o dicionário de colunas embutido na descrição do input. Era ela que transformava “quais são os watermelons” em DAX.

Sem ela, o agente ficou com duas queries fixas — EVALUATE 'Short Name' e EVALUATE 'tabela_agente' — e nenhuma capacidade analítica.

04 A skill migrada chama tools que não existem

A inicio-de-conversa manda “Call the Power BI detailed-query tool (PowerBI - Execute a query against a dataset)”. Nenhuma tool do agente se chama assim.

Skills referenciam tools por nome visível, em texto. Se o nome não bate, o agente não dá erro — ele improvisa, que é pior. E a tool Inicio de Conversa tem exatamente o mesmo nome da skill inicio-de-conversa, num sistema onde o roteamento é semântico.

05 As instruções leem uma variável que morreu

- MEMORY ALREADY FILTERED: The internal memory
  'Global.tabela_pbi' is ALREADY filtered for
  active/recent projects.

Global.tabela_pbi era criada pelo nó ParseValue do tópico de abertura. Sem o tópico, a variável não existe — o agente segue uma instrução impossível. E o texto veio com escapes literais de markdown (\*, \_) e a numeração das seções quebrada.

O modelo mental novo

Onde cada peça do agente antigo passa a viver. No clássico você era desenhista de fluxo; aqui você é redator de comportamento.

InstructionsSempre no contexto. Persona, vocabulário do negócio, regras inegociáveis, roteamento de alto nível.
SkillsSob demanda. Arquivos Markdown com o passo a passo de uma tarefa. É aqui que os tópicos renascem.
ToolsQuando preciso. Conector, MCP, agent flow. Tradução 1:1 das antigas ações.
KnowledgeQuando preciso. SharePoint, Dataverse, Microsoft IQ. Suas duas fontes migraram intactas.
MemoryEntre conversas. Capacidade nova, já ligada no seu agente.

Skills, em uma tela

Uma skill é um arquivo Markdown com frontmatter YAML. Só isso.

---
name: project-deep-dive        # kebab-case, ≤64 chars, = nome da pasta
description: >                 # ≤1024 chars — o CONTRATO DE ATIVAÇÃO
  Análise profunda de UM projeto... Use quando o usuário citar
  o nome ou o ID de um projeto... NÃO use para visão macro
  (use portfolio-overview).
---

## Passo 1 — Resolver nome → Work Item ID
Chame a tool **`Power BI Master DB Search`** com: ...
O erro nº 1 de quem vem dos tópicos

No clássico o gatilho era literal: triggerPhrases: ["preparar reunião", "pauta"]. Aqui não existe trigger phrase — a ativação é semântica, comparando a intenção do usuário com a description.

Por isso toda description deste projeto segue o mesmo padrão: o que faz + com que dados + quando usar + quando NÃO usar. O “quando não usar” é o que impede duas skills de brigarem pela mesma pergunta.

A armadilha que vai te pegar de novo

Toda vez que você cria uma tool, o Copilot Studio marca todos os inputs como “preencher dinamicamente com IA”. Você precisa ir em cada um dos fixos — groupid, datasetid, account, project, typeName — e trocar para “Valor personalizado”. Foi exatamente isso que quebrou a Master DB Search.

A ordem de execução

Cada etapa tem um teste de aceite. Não avance sem ele passar — senão você acumula erro e não descobre qual peça quebrou.

  1. SettingsIdioma para pt-BR, moderação de Máxima para Alta. Teste: escreva “olá”, ele responde em português.
  2. InstruçõesCole do arquivo .md cru — nunca de editor rico, é assim que os \* entram. Teste: reabra e procure por escapes.
  3. Tools, uma por vezComece corrigindo a Master DB Search. Teste cada uma no painel antes de criar a próxima.
  4. KnowledgeConfirme as duas fontes SharePoint. Teste: “o que é a fase 09 PGLS?”
  5. SkillsApague a antiga primeiro. Suba os seis .zip — o .md solto não carrega a pasta references/.
  6. Greeting & promptsOs três atalhos voltam aqui, como chips clicáveis. Dentro da skill eles são só texto.
  7. Testes ponta a pontaUm por skill. Se falhar, o culpado quase sempre é o nome da tool citado na skill não bater com o real.
  8. Publicar e repetir no TeamsA tool do Teams usa credencial de usuário final e se comporta diferente fora do painel de teste.

Duas decisões que são suas

Determinismo — o que você perde de verdade

A restrição da pauta executiva era Power Fx que executava: Or("nicolas.kuhnast@unilever.com" in Lower(System.User.Email), ...). Não tinha como contornar.

Numa skill, a mesma regra vira texto. Um modelo obedece na maioria das vezes — mas é uma instrução, não um portão. Se for crítico, precisa sair da skill: grupo de segurança, agente separado para os quatro, ou workflow com nó de condição.

Teams — a combinação que só o teste revela

Para mandar DM ao gestor, o par poster / location varia por tenant. Não dá para determinar isso pelo arquivo. Teste mandando mensagem para você mesmo, descubra o que funciona, e trave os dois em “Valor personalizado”.

Todo GUID, operationId, coluna DAX e reference name Custom.* foi extraído do botContent.yml do agente clássico e conferido linha a linha. Nada foi inventado.
